# What is kawa?

**kawa** is a high-performance, transparent gateway for Apache Kafka. It speaks the
Kafka wire protocol, so any standard Kafka client — producer, consumer, admin client,
streams app — can connect to it as if it were a broker. No client libraries, no
recompilation, no code changes.

kawa sits between your clients and your Kafka cluster:

```text
+------------------+       +----------------+       +------------------+
|  Kafka clients   | <---> |     kawa       | <---> |  Kafka cluster   |
| (any protocol    | 9092  |  (gateway)     |       | (bootstrap       |
|  version)        |       |                |       |  servers)        |
+------------------+       +----------------+       +------------------+
```

## Features

- **Transparent proxying** — clients connect to kawa on a regular Kafka listener;
  every request is decoded, forwarded to the right broker and the response is mapped back.
- **Virtual topics** — clients use logical topic names (e.g. `orders.eu`) that are
  rewritten to physical topics (e.g. `orders-v2`) in both directions. Physical topics
  stay hidden from Metadata responses by default.
- **Server-side consume filters** — drop records during Fetch based on record headers
  (`headerEquals`) or arbitrary [CEL](https://cel.dev) expressions (`cel`), with offsets
  preserved so consumers keep working normally.
- **Advertised-listener rewriting** — every broker/coordinator endpoint in Metadata and
  FindCoordinator responses is rewritten to point at the gateway, so all traffic flows
  through it.
- **Access control (RBAC)** — role-based ACLs enforced on the client-to-broker path
  (per-topic Produce, topic create/delete, consumer-group management), default-deny.
- **Observability** — Micrometer metrics for requests, latency, bytes and virtual-topic
  hits, with an optional Prometheus text-format endpoint.

## How it works

1. A client connects to a kawa listener and negotiates API versions.
2. kawa decodes each request using its built-in Kafka protocol codecs.
3. Interceptors rewrite the request (virtual topic mapping, filters).
4. The request is forwarded over a dedicated connection to the partition leader.
5. The response is decoded, mapped back (logical names restored, endpoints rewritten)
   and returned to the client.

APIs outside kawa's decode set pass through untouched.

## Modules

| Module | Purpose |
|---|---|
| `kawa-config` | YAML configuration model and loader |
| `kawa-core` | Transport-agnostic core: lifecycle, interceptor pipeline, routing, metadata cache |
| `kawa-protocol-kafka` | Kafka wire protocol: framing, headers, body codec, version strategy |
| `kawa-virtual-topic` | Virtual topic interceptor, per-API rewriters, consume filtering |
| `kawa-rbac` | Role-based access control: authorizer and per-API authorization checks |
| `kawa-server` | Netty server, broker connections and request dispatch |
| `kawa-integration-tests` | Testcontainers integration tests against a real Kafka cluster |

## Current scope and limitations

kawa is early-stage (milestone 1). Be aware of the following limitations:

- Plaintext connections only — no TLS yet (SASL authentication and RBAC are supported).
- Single upstream cluster per gateway.
- Routing relies on the standard Kafka client behaviour of retrying against the new
  leader after a `NOT_LEADER` error; no leader-forwarding inside the gateway.
- The advertised host must be resolvable **from the client's perspective**, since all
  broker endpoints are rewritten to point at the gateway.
